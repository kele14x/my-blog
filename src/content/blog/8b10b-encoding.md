## 从 UART、SPI 说起

如果你用过单片机，可能已经通过 UART 打印过调试信息，或者通过 SPI 读过传感器。把一个字节拆成 8 个比特逐个发送，听起来并不复杂。但接收端还需要知道一件事：**什么时候采样，才能知道现在读到的是哪一位？**

UART 和 SPI 用不同的方法回答这个问题：

- **SPI 另外发送时钟。** 主设备通过 `SCK` 时钟线告诉接收端何时采样，双方按约定的时钟边沿读写数据。即使数据线上连续出现很多个 0，时钟仍然在告诉接收端：“下一位到了。”
- **UART 逐帧重新对齐。** 它没有随数据发送的时钟线，收发双方先约定波特率和帧格式。以常见的 8N1 为例，一帧包含 1 个起始位、8 个数据位和 1 个停止位。接收端检测起始位的边沿，再按本地时钟采样后续数据；停止位标明帧的结束。双方时钟只需在这一帧内保持足够接近，下一帧的起始位又提供一次重新定时的机会。

它们通常不做 8b/10b 这样的块编码：**数据位本身按原来的值发送，定时则靠时钟线或帧结构来解决。** UART 的 8N1 虽然也用 10 个比特发送一个字节，但它是在原来的数据位两端加上起始位和停止位，不是把整个字节替换成一个经过挑选的 10-bit 码字。

## 高速链路为什么要改写数据？

一些高速串行链路选择不随数据另外发送时钟，而让接收端从数据电平的跳变中恢复采样时钟。额外的时钟线不仅增加布线，还要处理时钟与数据到达时间不同的问题；在高速下，一个比特的时间很短，这种时间差会变得更难处理。

现在假设直接连续发送很多个 `0x00`：数据线上就是一长串 0，没有跳变。接收端的本地时钟不会因此停下来，但缺少了用来校正采样时刻的线索。**如果能保证每隔几位就有一次电平跳变，从数据中恢复时钟就容易多了。**

与此同时，链路还可能采用电容或变压器耦合。这类连接不适合长期传递偏向某一电平的信号：如果 0 和 1 严重不平衡，接收端的信号基线可能漂移，影响判决。于是还希望编码后的码流中，0 和 1 的数量长期接近平衡，也就是**直流平衡**。

注意，这是两个不同的要求：**足够的跳变服务于时钟恢复，直流平衡服务于耦合与信号质量。** 0 和 1 总数一样多，并不保证不会出现一长串 0；反过来，经常跳变也不保证两者数量平衡。好的线编码需要同时照顾这些约束。

## 8b/10b 做了什么？

[8b/10b](https://en.wikipedia.org/wiki/8b/10b_encoding) 的名字很直观：把一个 8-bit 数据字节换成一个 10-bit 符号，再在线路上发送。它不是压缩或加密，而是给传输的数据“换一种更适合走线路的写法”，因此属于[线编码](https://en.wikipedia.org/wiki/Line_code)。接收端按同一套规则，把这些符号还原成原来的字节。

本文讨论的是 IBM 的经典方案，由 A. X. Widmer 和 P. A. Franaszek 在 1983 年的论文 [《A DC-Balanced, Partitioned-Block, 8B/10B Transmission Code》](https://ieeexplore.ieee.org/document/5390392) 中发表。它不会随意选一个 10-bit 比特串，而是根据当前字节和之前的编码状态，挑选满足传输约束的码字。

这样改写数据，主要换来三个好处：

- **时钟恢复**：合法码流中连续的 0 或 1 最多为 5 个，让接收端不断获得校正采样时刻的线索。
- **直流平衡**：把码流中 1 与 0 的累计数量差限制在很小的范围内，抑制直流和低频分量，有利于交流耦合、变压器耦合，并减轻基线漂移。
- **部分检错能力**：接收端可以发现非法码字，以及某些不符合编码状态的码字。不过，这不能检测所有传输错误，也不能自动纠错。

这些好处不是免费的。每 8 个数据比特要发送 10 个线端比特，因此相对于有效载荷，比特数增加了 `(10 - 8) / 8 = 25%`；只考虑数据编码时，有效载荷占线端比特的 `8 / 10 = 80%`。协议中的控制字符等还会进一步降低有效载荷比例。**8b/10b 的价值是让数据更适合传输，而不是用更低的线端比特率获得相同吞吐量。**

理解了为什么要多发这两个比特，接下来再看编码器如何挑选码字。完整编码表默认折叠，不必一开始就背下来；只想先看一次具体编码的话，也可以直接读后面的 `0xDEAD` 例子。

## 编码器

8-bit 字节记作 `HGFEDCBA`，编码后的 10-bit 符号记作 `abcdeifghj`，按 `a、b、c、d、e、i、f、g、h、j` 的顺序发送。其中：

- 低 5-bit `EDCBA` 编码成 6-bit `abcdei`；
- 高 3-bit `HGF` 编码成 4-bit `fghj`。

除了数据字节，链路还需要发送用于同步、标记边界等用途的**控制字符**，具体含义由上层协议规定。编码器通常接收一个字节和一个 `isK` 标志：`isK = 0` 表示普通数据，`isK = 1` 表示控制字符。这个标志只是告诉编码器如何解释输入，不是可以任意携带信息的第九位有效载荷。

数据字符记作 `D.x.y`，其中 `x` 的范围为 `0~31`，`y` 的范围为 `0~7`，共 256 种。控制字符记作 `K.x.y`，只定义了 12 种，完整清单见后面的折叠表。当 `isK = 1` 时，输入必须是这些合法控制字符之一，不能把任意字节都当成控制字符。

编码结果不仅与当前输入有关，还与之前的编码有关。编码器维护两个状态：`RD = -1` 和 `RD = +1`。RD 是 Running Disparity，本文称为**运行差异**；它是带有初始约定的历史偏差状态，用来决定下一子块应选择哪一种码字，而不是简单地从空码流开始计算 `1 的数量 - 0 的数量`。例如，尚未发送任何数据时，实际计数差为 0，但本文采用的初始 RD 为 `-1`。

下面是编码器的整体流程。代码仅为伪代码，循环范围包含两端：

```text
rd = -1
for i = 0 to length(instream) - 1
    input = instream[i]
    [sym, rd] = encode_8b10b(input.data, input.isK, rd)
    outstream[i] = sym
end
```

一次 8b/10b 编码可以拆成两步。以下位切片也包含两端；`data[4:0]` 表示 `EDCBA`，`data[7:5]` 表示 `HGF`，`concat` 按发送顺序拼接：

```text
function encode_8b10b(data, isK, rd)
    [six_bits, rd] = encode_5b6b(data[4:0], isK, rd)
    [four_bits, rd] = encode_3b4b(data[4:0], data[7:5], isK, rd)
    sym = concat(six_bits, four_bits)
    return [sym, rd]
end
```

注意，**3b/4b 编码使用的是 5b/6b 编码后更新的 RD**，并且不仅与高 3-bit 有关，也与低 5-bit 有关。

### 这些码表适用于哪一种方案？

下面的码表采用 **IBM Widmer/Franaszek 在 1983 年提出的经典 8b/10b 方案**。

后续的专用方案或变体，可能为了各自的设计目标采用不同的码字映射，但不一定与这里的 IBM 方案兼容。这里需要区分两件事：

- **实现方法不同**：用 ROM 查表、组合逻辑或流水线实现编码器，都可以输出同一套码字。电路或代码不同，不代表码表不同。
- **线上映射不同**：如果某个系统真的采用另一套码表，就必须按它自己的协议文档编解码，不能直接套用本文的表。

**在同一种标准化协议中，发送端和接收端必须遵守该协议规定的映射、控制字符与 RD 规则，不能单方面换表。** 否则接收端可能读成另一个字节，或者把收到的码字判为错误。

表中的比特串均按发送顺序书写；如果两个 RD 状态使用同一码字，两列会重复列出。下表供按需查阅，读懂后面的例子并不要求先记住整张表。

### 编码器状态机

编码器在每个 6b 或 4b 子块的边界更新 RD。本文从 `RD = -1` 开始，更新规则为：

- 子块偏差为 `+2`，更新为 `RD = +1`；
- 子块偏差为 `-2`，更新为 `RD = -1`；
- 子块偏差为 `0`，RD 保持不变。

当入口 `RD = -1` 时，只输出偏差为 `+2` 或 `0` 的子块；当入口 `RD = +1` 时，只输出偏差为 `-2` 或 `0` 的子块。这样的选择限制了累计偏差，是码流能够保持长期直流平衡的原因。

更严格地说，对于两个完整 10-bit 符号边界之间的合法码流，1 与 0 的累计数量差的绝对值不超过 2；这不表示任意截取的比特窗口都满足这个界限。前面所说的“数量长期接近平衡”，就是在这样的编码约束下实现的。

不过，**子块自身平衡，不代表它的码字与 RD 无关**。例如数据子块 `D.7.y` 的 `111000` 与 `000111`，以及 `D.x.3` 的 `1100` 与 `0011`，都必须按入口 RD 选择。这两个例子虽然不改变 RD，却仍然参与游程约束。控制子块也有 RD 相关的平衡形式，例如 `K.x.1`，不能简单地认为所有平衡编码都只有一种输出。

### 一个例子

以 `0xDEAD` 为例，明确按字节序列 `0xDE`、`0xAD` 依次发送，两者都是数据字符。这是本例选择的发送顺序，不代表所有协议对多字节整数都采用这个字节序。

- `0xDE = 11011110`，对应 `D.30.6`；
- `0xAD = 10101101`，对应 `D.13.5`。

从初始 `RD = -1` 开始，逐步查表：

<div style="overflow-x: auto;">

| 步骤 | 输入子块 | 输出 | RD 变化 |
| --- | --- | --- | --- |
| 1 | DE 的 D.30.y | `011110` | `-1 → +1` |
| 2 | DE 的 D.x.6 | `0110` | `+1 → +1` |
| 3 | AD 的 D.13.y | `101100` | `+1 → +1` |
| 4 | AD 的 D.x.5 | `1010` | `+1 → +1` |

</div>

最终得到：

```text
011110 0110 101100 1010
```

从左至右发送，空格仅用于区分子块；实际发送的是两个连续的 10-bit 符号。

## 解码器

在已知 10-bit 符号边界的前提下，解码器可以通过完整码字的反向查表，还原字节以及数据／控制标志。不能把任意两个各自合法的 6b、4b 子块拼接起来，就认为它们一定构成合法的 10b 符号。

### 符号定位

`K.28.1`、`K.28.5`、`K.28.7` 包含用于同步的“逗号”模式，可以辅助定位 10-bit 符号边界。具体使用哪个控制字符、何时发送以及是否周期性发送，取决于上层协议，不能把它们视为可以任意互换的同步符号。

尤其要注意 `K.28.7`：它与某些相邻码字的拼接可能形成错位的伪逗号，因而需要额外的同步处理，不能仅凭短逗号模式无条件重新对齐，也不能连续发送多个 `K.28.7`。实现时应遵循所用协议的控制字符和同步规则。

### 解码器状态机

如果只关心从完整合法码字还原出字节，解码器可以不维护历史 RD。但要检查码字是否符合当前的运行差异规则，就需要维护并更新 RD。

因此，非法码字检查和 RD 检查是两种互补的检错手段。某些传输错误仍然可能把一个合法码字变成另一个符合当前 RD 的合法码字，所以通过这些检查不代表数据一定正确。

## 一个实际应用：CPRI

8b/10b 并不只是教科书里的码表。一个典型应用是 CPRI（Common Public Radio Interface）：在基站中，它用来连接基带处理单元和射频单元，传输 I/Q 采样、控制与同步信息。

| 10 | 24.33024 | 64b/66b |

</div>

以选项 7 为例，线路上每秒发送 9.8304 Gbit，去掉 8b/10b 的编码开销后，对应 7.86432 Gbit/s 的编码前信息流。这部分信息流除了 I/Q 采样，还包括 CPRI 的控制与同步内容。

### 从 8b/10b 到 64b/66b

到了更高的吞吐量，8b/10b 的开销就显得有些昂贵了。每增加一份有效数据，都要在线路上多发送四分之一的比特。

64b/66b 则把 64 个比特编码为 66 个比特，开销小得多。用同样的口径比较：

- **8b/10b**：每 8 位多发 2 位，开销为 `2 / 8 = 25%`。
- **64b/66b**：每 64 位多发 2 位，开销为 `2 / 64 = 3.125%`。

换句话说，同样传输 64 位数据，8b/10b 要发 80 位，64b/66b 只需要发 66 位。上表中的 CPRI 选项 8 和 10 就采用了 64b/66b，把更多线路带宽留给编码前的信息流。

64b/66b 采用短同步头配合扰码来组织传输，不再沿用这套逐字节的 8b/10b 码表。编码的目标没有变：仍然是让接收端更容易处理收到的比特流，只是在高速链路上，带宽效率变得更加重要。

## 小结

IBM 8b/10b 以相对于有效载荷增加 25% 的线端比特数，换取直流平衡、有界游程和控制字符，便于交流耦合、时钟恢复与符号定位。理解编码器时，关键是区分整个符号与两个子块的入口 RD，并遵守 A7 的选择规则；理解解码器时，则要区分码字还原、符号同步和运行差异检查。

它能检测部分编码错误，但不是纠错码。实际链路中的可靠性，还需要上层协议配合校验、纠错或重传等机制。
